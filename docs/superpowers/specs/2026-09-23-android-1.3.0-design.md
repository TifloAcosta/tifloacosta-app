# Android 1.3.0 design

Date: 2026-09-23

## Goal

Turn the next Android beta into a meaningful functional release rather than a one-line notification hotfix. Android 1.3.0 must finish the native notification flow correctly, make notification taps useful, improve how users identify fresh items in Actualidad, and expose the installed app version for beta support.

The release must not be considered complete merely because the project compiles or CI is green. The acceptance criteria below require the notification integration to be genuinely connected and covered by automated checks. Physical-device validation remains an explicit pending item until Tony has an Android device available.

## Context

Android 1.2.0 (versionCode 7) was published to the closed Alpha track with the OneSignal Capacitor dependency present, but the app still instantiates the notification service with `createNotificationService(null)`. As a result, the Settings > Notifications interface exists but cannot reach a native adapter and reports notifications as unavailable.

The existing notification design remains valid in product terms: permission must be user-initiated from Settings, Android and Web Push audiences must remain distinguishable, and notification clicks may carry an internal destination.

Android 1.3.0 fixes the missing native connection and bundles it with related product improvements.

Tony does not currently have an Android device available for direct physical validation. The implementation, automated verification, signed build and closed-test release preparation may proceed without that device. The lack of physical testing must remain clearly recorded and must never be presented as if the end-to-end notification path had already been verified on hardware.

## Scope

### 1. Complete native Android notifications

- Keep the existing Settings > Notifications section.
- Do not request notification permission automatically at app startup.
- Initialize OneSignal silently when the Android app starts.
- Replace `createNotificationService(null)` with a real Android adapter backed by the official OneSignal Capacitor SDK.
- The adapter must expose:
  - current permission state;
  - explicit permission request;
  - opening Android notification settings after denial;
  - notification click events;
  - optional Android-client tagging for audience management.
- The existing Activate notifications button must trigger the Android permission request only after the user presses it.
- Authorized, denied, not-requested and unavailable states must remain understandable with different screen readers.
- Android subscriptions must be targetable separately from existing Web Push subscriptions.

### 2. Open the useful destination from a notification

A notification may include an internal TifloAcosta destination. Supported destinations for 1.3.0:

- general: open Home;
- news: open the selected Actualidad item in the existing clean reader;
- video: open the selected video in the accessible player;
- resource: open the selected resource using the current resource flow;
- download: open the existing download-link flow.

The app must validate all supplied notification data. Invalid, stale or incomplete data falls back to Home.

Notification taps must work when the app is:

- already open;
- in the background;
- launched from a stopped state.

If the click arrives before routing/content initialization is ready, keep a pending destination and process it only after normal startup is ready.

No destination may bypass the existing accessible flows or duplicate screen logic.

### 3. Identify new items in Actualidad

Add a lightweight local seen-state for Actualidad so users can distinguish items that appeared since their previous visit.

Product behavior:

- Use stable news IDs as the primary identity, not titles.
- Maintain local state only on the device; no account or server tracking is introduced.
- On first use of this feature, establish a baseline from the current catalog so the existing backlog is not announced as hundreds of new items.
- On later refreshes, items whose IDs were not present in the previous baseline are treated as new until the user visits Actualidad.
- The Actualidad screen must expose the number of new items near the top in plain text that a screen reader can read naturally.
- Each new article should include a short accessible text marker such as `Nuevo` before or near its title. Do not rely on color alone.
- Opening or visiting Actualidad updates the seen baseline in a predictable way. The implementation should avoid repeatedly announcing the same item as new after the user has already visited the section.
- This feature must remain useful offline when cached content is being shown.

The design intentionally avoids per-article manual read/unread management for this release. The goal is simply to answer: “what appeared since I last checked Actualidad?”

### 4. Show installed version information

Add a small app-information block in Settings.

It must show at least:

- app version name;
- Android versionCode/build number.

The values must come from the installed native package/build metadata rather than hard-coded display text whenever practical.

This is primarily a beta-support feature: when a tester reports a problem, Tony can ask them to read the version shown in Settings and immediately confirm which build is installed.

The information must be plain accessible text, not a visually-only footer.

## Accessibility requirements

- Do not make the notification experience TalkBack-specific.
- Preserve semantic HTML controls and heading structure.
- Permission/status changes should continue to use an appropriate live region without forcing focus.
- New markers in Actualidad must be meaningful when spoken and must not depend on color, position or icons alone.
- Notification-driven navigation must preserve the existing heading-focus behavior of the target screen.
- No notification or Actualidad change may introduce automatic speech loops, repeated focus jumps or autoplay.
- Spanish and English strings must be added together for every new user-facing message.

## Technical structure

### Notification adapter

Create a real adapter module around the official OneSignal Capacitor SDK. The application layer must depend on the existing notification service abstraction, not on raw OneSignal calls scattered across screens.

The adapter is responsible for SDK initialization and native permission/system-settings operations. Routing remains outside the adapter.

### Notification destination resolver

Keep destination parsing/resolution independent of OneSignal so it can be unit-tested with plain objects.

The resolver converts validated payloads into existing app actions and falls back safely to Home.

### Actualidad seen-state

Add a small storage module dedicated to the last known set/baseline of news IDs. Keep it separate from favorites and content caching.

The screen receives already-derived `isNew` information rather than embedding storage policy in every card.

### Version metadata

Use Capacitor/native app metadata where available. If the current Capacitor App plugin does not expose build number directly in the existing setup, add the smallest native bridge needed rather than duplicating version strings in several places.

## Release acceptance gates

Android 1.3.0 must not be declared ready for Play Console unless all of the following software-verifiable gates are true:

1. Production app startup no longer contains `createNotificationService(null)`.
2. An automated test fails if the Android notification service is disconnected or replaced with a null adapter.
3. The OneSignal SDK is initialized through the real adapter.
4. Settings can represent not-requested, authorized and denied permission states.
5. The Activate notifications action reaches the native permission request path.
6. Notification click payloads are unit-tested for general, news, video, resource, download and invalid data.
7. Startup-from-notification is tested so early click events are queued and processed once routing/content are ready.
8. Actualidad new-item tracking has regression tests for first-run baseline, newly arrived IDs and repeated visits.
9. Version/build information is covered by a test or verified native metadata path.
10. Existing mobile test suite passes.
11. Signed Android build succeeds.

### Deferred physical-device validation

A real Android-device test remains required before we claim that native notifications have been validated end to end on hardware. Because Tony does not currently have an Android device available, this check is explicitly deferred and is not a blocker for implementation, automated verification, signed build generation or preparing/publishing the closed-test beta.

When an Android device becomes available, the deferred validation must cover at least:

- activation of notification permission from Settings;
- receipt of a real OneSignal test notification;
- understandable output with an Android screen reader;
- tapping the notification and opening the expected TifloAcosta destination;
- foreground, background and stopped-app behavior where practical;
- absence of duplicate notifications or duplicate navigation.

Until that physical test is performed, the release notes and tester communications must not state that the notification flow has been physically verified. They may state that the feature is included for beta testing.

## Versioning

Target release:

- versionName: 1.3.0
- versionCode: 8

The version bump should be one of the last implementation steps, after the feature work is complete and verified, so intermediate work cannot accidentally be mistaken for a release candidate.

## Out of scope

- YouTube alternate audio-track selection. The embedded player API does not currently provide the required reliable control, so it should not be bundled as a half-working feature.
- Per-topic notification subscription controls.
- Custom notification sounds or rich layouts.
- Accounts or cloud sync for read/unread news state.
- A full per-article unread inbox.
- Changes to the existing Web Push experience other than preserving audience separation.

## Success criteria

The software side of Android 1.3.0 is considered ready for closed beta when the native notification adapter is connected, permission and routing paths are covered by automated tests, Actualidad can identify newly arrived items, Settings exposes version/build information, the complete mobile suite passes and a signed build is produced.

Physical confirmation of real notification delivery and opening remains a separate, explicitly pending validation until an Android device is available.
